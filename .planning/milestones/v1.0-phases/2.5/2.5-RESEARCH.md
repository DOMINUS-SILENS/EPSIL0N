# Phase 2.5: Runtime Spine - Research

**Researched:** 2026-04-06
**Domain:** Event-Sourcing Runtime Infrastructure
**Confidence:** HIGH

## Summary

The Runtime Spine transforms the EPSILON kernel from a collection of semantic primitives into an operational execution engine. The core of this "spine" is the cycle of **Load $\rightarrow$ Mutate $\rightarrow$ Save**, orchestrated by a generic Event-Sourced Repository that bridges `AggregateRoot` and `IEventStore`.

The current implementation of `PostgreSqlEventStore` provides basic append/load capabilities but lacks hardened concurrency enforcement at the database level and lacks a coordinating repository. This research defines the architectural requirements to implement a production-grade runtime spine.

**Primary recommendation:** Implement a generic `EventSourcedRepository` that encapsulates the rehydration logic and enforces tenant isolation by requiring a `SecurityContext` or explicit `TenantId` for every operation.

### Pattern 1: The Load-Mutate-Save Cycle
**What:** The deterministic flow of aggregate interaction.
**When to use:** All mutating operations in the application layer.
**Sequence:**
1. **Load**: `Repository::getById(id, tenantId)` $\rightarrow$ `EventStore::load(tenantId, streamId)` $\rightarrow$ `AggregateRoot::reconstituteFromEvents(events)`.
2. **Mutate**: Call business method on aggregate $\rightarrow$ `AggregateRoot::raise(event)` $\rightarrow$ `AggregateRoot::apply(event)`.
3. **Save**: `Repository::save(aggregate)` $\rightarrow$ `AggregateRoot::popUncommittedEvents()` $\rightarrow$ `EventStore::append(tenantId, streamId, expectedVersion, events)`.

### Anti-Patterns to Avoid
- **Ambient Tenant State**: Never use a global "CurrentTenant" singleton in the repository. Pass `TenantId` explicitly to prevent leakage.
- **Manual Version Management**: The repository must determine the `ExpectedVersion` from the aggregate's `streamVersion`, not the caller.

## Common Pitfalls

### Pitfall 1: Race Conditions in `append()`
**What goes wrong:** Two processes read version 5, both try to write version 6.
**Why it happens:** Relying on `getStreamVersion()` followed by `INSERT` is not atomic.
**How to avoid:** Create a UNIQUE constraint on `(stream_id, stream_version)`. Let PostgreSQL reject the second insert.
**Warning signs:** Intermittent `ConcurrencyConflictException` that doesn't match the application's version tracking.

### Pitfall 2: Serialization "Class Not Found"
**What goes wrong:** Replaying events from a renamed class.
**Why it happens:** Storing fully qualified class names (FQCN) in the database.
**How to avoid:** Use an `event_type` alias (e.g., `order.created`) and a mapping registry.

## Code Examples

### Proposed `EventSourcedRepository` Signature
```typescript
// Note: Conceptual TypeScript for structure, implementation in PHP
class EventSourcedRepository<T extends AggregateRoot> {
    constructor(private eventStore: IEventStore, private aggregateClass: class<T>) {}

    async getById(id: string, tenantId: TenantId): Promise<T> {
        const events = await this.eventStore.load(tenantId, `${this.aggregateClass.name}:${id}`);
        const aggregate = new this.aggregateClass(id, tenantId);
        aggregate.reconstituteFromEvents(events);
        return aggregate;
    }

    async save(aggregate: T): Promise<void> {
        const events = aggregate.popUncommittedEvents();
        const expectedVersion = ExpectedVersion.exact(aggregate.getStreamVersion());
        const newVersion = await this.eventStore.append(
            aggregate.getTenantId(),
            `${this.aggregateClass.name}:${aggregate.getId()}`,
            expectedVersion,
            events
        );
        aggregate.markCommitted(newVersion);
    }
}
```
